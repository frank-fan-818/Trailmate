# ADR-002: LLM 调用链路质量韧性加固

## 状态

Accepted (2026-05-27)

## 场景

项目当前通过 OpenRouter 调用 LLM（MiniMax 等模型）来支撑 AI 旅行管家和行程规划两大核心功能。
现网运行的 `callLLM()` 缺乏以下关键保护：

1. **无超时控制** — `fetch()` 没有 `AbortController`，网络抖动时请求可能无限挂起，用户界面永久转圈。
2. **无结构化日志** — 所有 `console.log` 都是非结构化文本，出问题时无法按 traceId 快速定位一条完整链路。
3. **无降级方案** — LLM 不可用时直接抛出异常，导致用户看到原始错误信息或空白页面。
4. **无 Evals** — 没有对 LLM 输出质量做量化评估，模型/提示词变更的影响无法衡量。

随着项目从 Demo 向真实用户可用演进，这四个问题会导致：故障排查效率低（日志不可检索）、用户体验差（不优雅降级）、质量无保障（无回归指标）。

## 决策

我们实施「三层防护」质量韧性方案：

| 层级 | 措施 | 实现 |
|------|------|------|
| **韧性层** | timeout 30s + 降级回复 | `callLLM()` 增加 AbortController 30s 超时；`runWithTools()` 在最外层 catch 返回友好降级文案 |
| **可观测层** | JSON 结构化日志 + traceId | `shared/utils/logger.ts` 提供 ENTRY/STEP/EXIT 三阶段日志；每次 AI 请求生成唯一 traceId 贯穿全链路 |
| **质量层** | Evals 脚本 | `evals/run-itinerary-eval.mjs` 对行程生成 LLM 节点做 15 次采样，统计格式合规率和内容准确率 |

**timeout 30s 的选择依据**：OpenRouter + MiniMax 模型典型响应时间 2-8 秒。包含 3 次重试（间隔 2s/4s），最坏情况 ≈ 30s + 6s = 36s。30s 的取值在「给正常调用留足余量」与「尽快失败让用户重试」之间取得平衡，是行业常用的非流式 LLM 超时值。

**日志的三层结构**：
```
ENTRY  → 记录请求进入（用户消息、上下文大小）
STEP   → 记录关键步骤（LLM 调用、工具执行）
EXIT   → 记录最终响应（内容长度、耗时、工具调用数）
```

## 后果

### 正面

- **故障排查**：出问题时按 traceId grep 即可看到完整链路，从用户输入到最终响应的每一步耗时和结果一目了然。
- **用户体验**：LLM 不可用时用户看到的是友好提示而非技术错误，体验从「炸了」升级为「暂时不可用」。
- **质量可衡量**：Evals 脚本给出明确数字（格式合规率 XX%、内容准确率 XX%），而非「感觉还行」。
- **低侵入性**：日志和超时改动仅在 `useOpenRouter.ts` 和 `useAiConcierge.ts` 两个文件，不影响其他模块。

### 负面

- **日志量增加**：每次 AI 请求产生 5-10 行 JSON 日志，控制台输出增加。可在后续引入日志级别过滤（WARN 以上才输出）来缓解。
- **Evals 开销**：每次运行 Evals 需消耗 OpenRouter API 配额（15 次 × 2000 tokens ≈ 30K tokens）。建议在 PR 合并前手动运行，而非每次 CI。
- **30s 超时可能仍显漫长**：对用户而言 30s 等待仍不够理想，后续可考虑流式响应（streaming）来改善体感。

### 后续待办

1. 日志级别过滤：开发环境全量输出，生产环境仅 WARN+
2. 流式 SSE 响应：替代当前的非流式调用，降低用户体感延迟
3. CI 集成 Evals：将 Evals 脚本加入 pre-release CI pipeline
4. 更多节点的 Evals：为旅伴匹配、通知生成等 LLM 节点补充 Evals
